# Local Dictation UI audit, 11 November 2026

## Scope and evidence

The app is a Windows WPF dictation utility. This review used the source,
current product requirements, and the existing synthetic native compact-Review
preview. Windows chrome, Segoe UI, familiar input controls, and the approved
pink waveform identity remain appropriate.

The apple-design skill supplied cross-platform principles for hierarchy,
accessibility, feedback, and direct text editing. Its macOS-specific menu,
window-control, and shortcut conventions are not Windows requirements.

Read references: accessibility, layout, typography, color, designing for macOS,
cross-platform translation, buttons, settings, windows, entering data, text
fields, and the code-audit companion. The references are bundled with that
skill; this was not a new online HIG verification.

## Findings and implementation direction

1. The shortcut can use the saved model while the settings form displays an
   unsaved selection. Record in banner already saved the form first; fixing
   only that button would miss the shortcut path. Persist valid discrete
   settings immediately, validate text drafts independently, and display save
   failures beside the relevant controls.

2. Native title chrome, a repeated large app heading, tab framing, and bordered
   cards produce too many containment levels. Keep native chrome and tabs;
   replace cards with aligned section headings and whitespace. Reserve the
   primary visual emphasis for Record, and remove Save after autosave covers
   every setting.

3. Compact Review originally displayed a TextBlock and required Details for
   whole-text editing. Make the existing transcript region editable, preserve
   exact text and provenance, and retain explicit insertion after manual edits.
   Details remains optional. Already-inserted items remain read-only.

4. The custom Button template centered all content, overriding the wording
   buttons' left-alignment setting. Template-bind content alignment and provide
   press feedback. Keep existing keyboard focus and familiar button sizes.

5. Selected text needs a separate semantic foreground in Windows High Contrast.
   Highlight backgrounds must use HighlightText, rather than ordinary WindowText.
   The banner and compact Review also need semantic contrast colors even though
   their normal dark palette is intentionally fixed.

6. The inactive waveform becomes a row of decorative dots during Review. Hide
   it then; preserve the recording waveform, header drag area, and placement.

7. Large-v3 Live was disabled by the advertised model capability. The source
   must distinguish supported live operation from measured latency readiness.
   This visual review does not establish model performance or justify a
   low-latency claim.

## Narrow audit implementation

BannerWindow collapses the waveform only while a Review is present. It keeps
all approved normal dark color values. In Windows High Contrast, its content
and surfaces use WindowText/Window, while the primary action and status tile
use HighlightText/Highlight. It refreshes those brushes when Windows changes
its contrast palette. The drop shadow is omitted in High Contrast.

ThemeManager adds SelectedInk. It equals ordinary Ink in normal Light/Dark
appearance and HighlightText in High Contrast. The settings templates consume
this separate foreground. Compact Review and settings changes are owned by
the corresponding implementation work, not by the banner change.

that system palette and must be checked in the application.

## Guideline basis

- Layout, Visual hierarchy: group related functions; containers are one option,
  not a requirement. Whitespace is sufficient for the settings sections.
- Settings, Task-specific options: let people modify relevant options in context.
- Buttons, Best practices: custom buttons need a visible press state.
- Text fields, Best practices: larger text entry belongs in a text view.
- Accessibility, Vision: sufficient contrast, larger text, and alternatives to
  color-only communication matter on every desktop platform.

## Verification boundary

Source review, exact-color contrast calculation, and scoped diff checks were
performed. The existing native preview was inspected; it predates these changes.
The final combined WPF build and synthetic interaction probes are recorded by
the main implementation task. No microphone, model inference, destination
injection, deployment, or Windows accessibility-setting change was performed
by this audit work. Real application insertion and live latency remain separate
acceptance checks.
